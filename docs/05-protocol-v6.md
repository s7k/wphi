# v6 プロトコル (可変サイズの視界) への対応

WPHI が地図の窓の大きさに合わせた視界をサーバへ要求し、返ってきた W×H マスの地図を描く為の設計。
WPHI 側は実装済み(v6 を送るサーバでの通し確認は未実施)。
サーバ側の行の書式と判断の理由は phi_dm の `docs/dev/protocol-v6.md` (`~/workspace/phidm-v6`) にあり、この資料はクライアント側の変更だけを扱う。

## 1. 目的と、拡張マップを取りやめる理由

v0.1.71 までの WPHI は、`#ex-pos` の届く世界で通った所の地形を覚え、7x7 の外に暗くして重ねていた (拡張マップ)。
v6 では外側の地形もサーバが送るので、拡張マップを取りやめる。

拡張マップには、v6 にすると消える次の制限がある。

- 通った事の無い所は描けない
- 覚えた地形は通った時点の物で、スイッチで開いた扉等が古いまま残る
- 外側のキャラは描けない
- 北固定 (solid) の時だけ働き、回転 (turn) では覚えない

v6 に対応しないサーバ (v5y 等) では 7x7 の地図だけになり、拡張マップの分の表示が無くなる。
古いサーバ向けに拡張マップを残すと、地図の作り方が 2 通りになり、予想の処理 (predict.ts) と描画の両方で分岐が要る為、残さない。

## 2. 送る行と、型の決め方

ログインの行 (`session.rs` の `login_lines`) の `#ex-map size=57` と `#ex-map style=` の後に、`#ex-map view=W H` を足す。
W と H は 3〜99 の奇数で、地図の窓に入るマス数から決める (下の 4)。

型はサーバの返事で決める。
送った値でなく返事で決める点は、今の `#ex-map style=` と同じ ([04-client-spec.md](04-client-spec.md) の 5.4)。

| 届いた行 | クライアントの状態 |
|---|---|
| `#ex-map view=W' H'` | v6。以後 `#v6` の行で地図が届く。W'、H' は要求より小さい事がある |
| `#ex-map view=no` | v6 でない。今の 7x7 のまま |
| 何も来ない (v6 に対応しないサーバ) | v6 でない。今の 7x7 のまま |

サーバは世界の移動 (ゲート) のたびに v6 の状態を消す。
WPHI は世界の移動の後 (`#ch-srv-ok` の後) にも `login_lines` を送り直している (session.rs の 437〜440) ので、`#ex-map view=` もそこで送り直す事になる。
今の `login_lines` は固定の行を返すだけで、窓の大きさを知らない。
`login_lines` に要求する W と H を引数で渡し、UI が最後に決めた大きさをセッションが持つ。

回転 (turn) は正方形だけを受け付け、サーバは W≠H の要求を小さい方に揃えた `view=N N` で返す。
WPHI は turn の時に最初から正方形を要求し、返事を待たずに画面の形を変えない。

## 3. 受ける行の解析 (crates/phi-proto)

### 3.1 行の形

```text
#v6 M (方角) (HEX時刻) W H
#v6 R (行番号) (チップ, 属性) の組が W 個
#v6 O (キャラ・物 1 つ)
#ex-pos x y
#v6 .
```

- `#v6 M` は 6 バイト目が方角 (N/E/S/W)、その後に 16 進 8 桁の時刻、10 進の W と H が空白で区切って続く
- `#v6 R` は `#v6 R NN ` の 9 バイトの後に 2W バイトが続く。NN は 10 進 2 桁の行番号で、0 が上の行
- `#v6 R` の (チップ, 属性) の符号化は `#m57 M` と同じ ([04-client-spec.md](04-client-spec.md) の 5.3)
- `#m57 M` と同じく、`#v6 R` は地形のバイト列なので cp932 へ変えずに扱う

`#v6 O` の欄の位置は `#m57 O` からずれる。
行の頭が 1 バイト短く、座標が 10 進 2 桁になる為。

| 位置 | 欄 | `#m57 O` での位置 |
|---|---|---|
| 6 | 層 (C/B/F) | 7 |
| 7〜11 | ID (16 進) | 8〜12 |
| 12〜14 | X (10 進 2 桁) | 13 (1 桁) |
| 15〜17 | Y (10 進 2 桁) | 15 (1 桁) |
| 18 | 向き (B/R/F/L) | 17 |
| 20〜51 | 名前 (cp932) | 19〜50 |
| 52〜54 | 状態 (16 進) | 51〜53 |
| 55〜70 | グラの名前 | 54〜69 |
| 71 | `*` なら巨大なキャラ | 70 |
| 73〜75 | 種別 (16 進) | 72〜74 |

長さが 75 バイトに満たない行は捨てる。
`#v6 O` の欄の解析は `parse_m57_o` に開始位置と座標の桁数を渡す形にして、`#m57 O` と共有する。

### 3.2 型の変更

`Map` の `size: u8` を `width: u8` と `height: u8` に替える。
`#m57` では両方 7 を入れる。
`Chara` の `x`、`y` は今の `u8` のままで足りる。

`MAP_CELLS=49` と `finish_map` の 7 は、`#m57` の中だけで使う値として残す。
`#v6` は `#v6 M` で読んだ W と H を使う。

`#v6 R` は届いた順に溜め、`#v6 .` で `Event::Map` を返す。
`#v6 .` の時点で H 行揃っていなければ、その地図は捨てて前の地図のまま描く。

### 3.3 テスト

今の出力比較テスト (`tools/golden/gen.py` と `tests/golden/parser.json`) は phi-client-web の Python 版のパーサを正解にしている。
Python 版は v6 を知らないので、v6 の解析は parser.rs の単体テストで確かめる。
書く例は次の物。

- 9x9 の solid の地図 1 枚 (M、R が 9 行、O、`.`)
- 座標が 10 以上のキャラ
- R が足りないまま `.` が来た時に、地図を返さない
- 11x7 のような W≠H の地図

`#m57` の出力比較テストは変えずに通す。

## 4. 画面 (ui)

### 4.1 要求する大きさ

地図の窓のマス数は、窓の幅と高さをマスの大きさ (32px) で割った数を、奇数へ切り下げた物にする。
窓の大きさが変わった時は、最後に変わってから 300ms 待ってから `#ex-map view=` を送り直す。
窓の端を引きずっている間に、毎フレーム要求を送らない為。

`#ex-map view=` で求めるのは、窓に入るマス数より上下左右に 1 マスずつ多い (W+2)×(H+2) にする (session.rs の `view_line`)。
turn は窓の幅と高さの小さい方を N とし、(N+2)×(N+2) を求める。
届いた地図の外周 1 マスは窓の外に置き、見せない (mapRender.ts の `viewArea`)。
スムーズ移動で地図を 1 マスずらす間、窓の端に入ってくる 1 列か 1 行に、この外周の地形とキャラを描く為。
外周が無いと、その 1 列か 1 行が黒いまま地図がずれ、カクついて見える。
予想 (4.4) で地図をずらした時に `?` で埋める端も外周に入り、窓には出ない。

サーバの上限は、行の書式 (行番号と座標が 10 進 2 桁) で送れる最大の 99×99 (phi_dm の `MAX_VIEW`、`MAX_VIEW_W` の既定)。
WPHI は外周を足して 99 を超えないように求める (session.rs の `view_line`)。
世界によっては phi_dm.cnf で上限を下げている。
上限に当たって要求より小さく届いた時も、届いた W'×H' の外周 1 マスを窓の外に置き、見せる範囲は (W'-2)×(H'-2) に狭まる。
窓は灰色のまま残り、`?` では埋めない。
届いた幅か高さが 5 より小さく、外周を除くと 3 に足りない時は外周も見せる。
窓を縮めた直後で、窓より大きい地図が届いた時は、中央の窓の大きさだけを見せる。

見せる範囲は、その中の自キャラが見せる大きさで決まる位置 (4.2 の表) に来るように置く。
北固定では外周が上下左右に 1 マスずつになる。
turn は自キャラが届いた大きさ M で決まる位置にいるので、上下の外周が 1 マスずつとは限らない。
M=11 の自キャラは 7 行目、見せる 9×9 の自キャラは 5 行目なので、上に 2 行、下に 0 行を外す。

### 4.2 自キャラの位置

| 型 | 自キャラの位置 (左上を 0 とする列, 行) |
|---|---|
| solid | ((W-1)/2, (H-1)/2) |
| turn (N×N) | ((N-1)/2, N-1-⌊N/3⌋) |

turn は前が上で、後ろに ⌊N/3⌋ 行、前に N-1-⌊N/3⌋ 行が見える。
N=7 で前 4 行、後ろ 2 行になり、`#m57` の turn と同じ形になる。

自キャラのマスは mapRender.ts の `selfPos` で上の表から決め、名前を出さないキャラ、吹き出しの基準、滑らかに動かす時の自キャラ、マウスの向きの基準に使う。
7x7 の `#m57` の回転でもサーバは自キャラを (3, 4) に置く (phi_m57.rs の set_view7 の SP=2) ので、`#m57` にも同じ表を使う。
v0.1.71 までは (3, 3) としていた為、回転の時に自キャラの1つ前のキャラの名前が出ず、自キャラの名前が出ていた。

### 4.3 描画

`gridDim(size)` は 5 か 7 の正方形を返している。
これを `width` と `height` の 2 つにし、drawMap.ts の `dim` を幅と高さに分ける。
eagleBoard.ts は届かなかったマスを `'?'` で埋めて描いているので、v6 の描画もこれと同じ作りにする。

### 4.4 位置の予想

今の予想 (predict.ts) は、北固定の `go` を送った後に地図が来なければ、進んだとみなして拡張マップを 1 マスずらしている。
拡張マップを取りやめた後は、最後に届いた v6 の地図を 1 マスずらし、新しく入る端の 1 行か 1 列を `?` で埋める。
予想を使う条件は、設定の「拡張マップ」から「v6 で solid の時」に替える。

### 4.5 消す物

- ui/src/automap.ts と automap.test.ts
- App.tsx の `recordAutomap`、`automaps`、`unsavedWorlds`、`AUTOMAP_EVENT` の送受信、メニューの `automap-clear`
- 設定の `automap`。設定は settings.json にあり、知らない項目は読む時に捨てるので、次に保存した時に消える
- localStorage に世界ごとに書いた地形 (32x32 の区画)。起動時に 1 回消す

### 4.6 イーグルアイ

v6 の視界は北固定で最大 31x23 を見せるので、15x15 のイーグルアイでは呪文の意味が無くなる。
そこでサーバは v6 の接続 (`#ex-map view=` が有効) にはイーグルアイを 65x49 (幅 65、高さ 49、約 4:3) で送る。
行の書式は変えず、行の頭は `#ex-eagleeye M 64 00 ` 〜 `#ex-eagleeye M 64 28 ` になり、自キャラは中央の (32, 14) にいる。
m57 の区域 (`FF_M57`) では v6 でも 11x11 のままで、v6 でない接続は今と同じ 15x15 か 11x11。

| 接続 | 区域 | 大きさ |
|---|---|---|
| v6 | m57 の区域 | 11x11 |
| v6 | それ以外 | 65x49 |
| v6 でない | m57 の区域 | 11x11 |
| v6 でない | それ以外 | 15x15 |

パーサ (parser.rs の `EagleEyeAccum`) は幅を行の頭から、高さを届いた行番号の最大 + 1 から決め、書式の 2 桁で書ける 99x99 まで受ける。
サーバは `#ex-eagleeye pos` を送らないので、自キャラの位置 (`self`) は盤面の中央 (幅/2, 高さ/2) にする。
EagleEye の窓は 1 マス 32px で canvas に描き、CSS の `object-fit: contain` で縦横比を保ったまま窓いっぱいに合わせる。
窓の既定の大きさは 65x49 が 1 マス 16px で入る 1040x784。

## 5. 未決事項

- サーバが phi_dm.cnf で上限を下げた世界では、モダンでも地図の周りが空く。倍率を上げて埋めるかを決めていない
- turn の時に窓が横長だと、N×N の地図の左右が空く。今の 7x7 の turn と同じ扱いでよいかを決めていない
- サーバのキャラの上限 (`MAX_PRINT_NPC`) を超えたキャラは届かない。サーバ側で近い順に切る案を勧めている為、遠くのキャラから消える

## 6. 実装で設計から変えた所

- 型を `#ex-map view=` の返事では決めず、`#v6` の地図が届いたかで決める (`Map` の `v6`)。v6 でないサーバは `view=` を読み捨てて何も返さず、返事を待っても `#m57` の地図が届くだけな為
- 回転の時に N×N に揃えるのは UI でなくセッション (session.rs の `view_line`) にした。サーバが `#ex-map style=` を返すたびに型に合わせて送り直すので、北固定へ戻った時も W×H を求め直せる。地図の窓は1つなので、UI は窓の大きさだけを `set_map_view` で全部のセッションへ知らせる
- 窓に入るマス数は、拡大率を掛けたマスの大きさ (32px × 拡大率) で割る
- 予想を使う条件は「v6 の北固定で、`#ex-pos` の届く世界」。予想は地図の位置のずれで返事を照らし合わせるので、`#ex-pos` が要る
- マウスで進む向きは、地図の中央でなく自キャラのマスから見て決める。回転の自キャラは中央より下にいる為
- 出力比較テストの正解データは Python 版の `size` のままにし、tests/golden.rs が比べる前に `width` と `height` に分ける。正解データを書き換えると Python 版が正解である事が崩れる為

## 7. 通信の圧縮と移動の返事

行の書式とサーバ側の判断は、phi_dm の `docs/dev/protocol-v6.md` の「通信の圧縮」と「移動の返事」にある。

### 7.1 圧縮

ログインの行 (`login_lines`) の最後に `#ex-switch compress=deflate` を送る。
世界移動の後も `login_lines` を送り直すので、移動先の接続でも求め直す。
対応していないサーバは読み捨てて何も返さず、圧縮しないまま届く。

受けたバイト列は、行に分ける前に session.rs の `Inflate` に通す。
`Inflate` は `\n#ex-switch compress=deflate\n` を探し、その後ろを zlib 形式として展開する。
返事の行が2回の受信に跨っても見つけるように、前に受けた分の末尾を残しておく。
世界移動で移動元の `#trs-ok` を待つ間 (`wait_line`) も、同じ `Inflate` を通す。
`WPHI_RECORD` に書くのは展開した後のバイト列にする。

### 7.2 移動の返事

`#v6 G dx dy` は `Event::Moved` (UI では `moved`) になる。
predict.ts は `moved` を一度でも受けると、次のように振る舞いを変える。

- `moved` で、一番古い返事の来ていない移動を確定する。1 マス動いた分は、地図が来なくても最後の地図からずらす
- 地図は `#v6 G` の後に届くので、地図が来たら確定した分を消す。前の地図との位置の差で返事を照らし合わせる処理は使わない
- 「進めません」は `#v6 G 0 0` と重なるので数えない
- 1.5 秒待っても返事の来ない移動は捨てる。移動先の選択の最中の `go` は番号として読まれ、返事が来ない為
- 返事を待ちきった移動を進んだとみなす処理は残す。回線が遅い時に、返事より先に動いて見せる為

### 7.3 スムーズ移動

表示の「マップを滑らかに動かす(試験中)」は、北固定の時に、自分が歩いた分だけ地図を前の位置から滑らせて描く。

自分の位置は、`#v6 G` を送るサーバでは predict.ts が数えた `walk` (1 マスずつ歩いた分の合計に、進んだとみなした分を足した物) を使う。
`walk` は `#v6 G` を受けた時点で変わるので、地図が届くのを待たずに滑らせ始める。
`#ex-pos` だけが届く世界では、地図の位置 (`map.pos`) を使う。
テレポートで1マスより大きく飛んだ時とタブを切り替えた時は `walk` の `epoch` を変え、滑らせずに描く。

`walk` には位置が変わった時刻 (`at`、窓をまたいで比べる絶対の ms) を付ける。
地図の側は、受けた位置と時刻を並べておき、今より少し前の時刻の位置を、前後の位置の間を直線で補って描く (mapRender.ts の `walkAt`)。
遅らせる時間は 130ms を下限に、続けて歩いている間の最近の間隔に合わせて延ばし、250ms を上限にする (`walkDelay`)。
止まっていた後の1歩目は、その 100ms 前まで前の位置にいた事にして、100ms で滑らせる (`addWalk`)。

位置を受けた時刻から滑らせ始める作りにしない理由は、main 窓から地図へ状態が届くまでの時間が 7〜26ms 揺れる為。
v0.1.76 はその作りで、届くのが遅れると前の1歩を滑り終えて止まり、長押しで歩くとガタガタに見えた。
同じ時のトレースの時刻を今の作りに流すと、24 歩の間 1 フレーム (16.7ms) に 5〜5.6px で動き、止まるのは歩き始めの 3 フレームだけだった。

滑らせる間は、地図を毎フレーム描き直さない。
周りに2マス広く描いた地図 (自キャラ以外) を1回だけ別の canvas に描き、毎フレームはそれをずらして写して自キャラを描く (map.tsx の `paint`)。
地図は自キャラより後ろの行と前の行の2枚に分け、後ろ → 自キャラ → 前 の順に重ねる。
止まっている時は上の行から順にチップとキャラを重ねるので、自キャラの1つ下の行の壁 (上へ 16px はみ出す) が自キャラの足元に重なる。
滑らせる間も同じ重なりにする為、自キャラの絵より完全に下にある最初の行から前の1枚に描く。
上下に滑らせる間は自キャラが行と行の間にいるので、その行は滑らせる量で変わり、変わった時に2枚を描き直す。
地図やアニメが変わった時だけ、その canvas を描き直す。
毎フレーム 900 ほどのチップを描くと、WebKitGTK では 1 回が 16ms を超え、フレームが落ちていた。
滑らせる間に `MapView` を React で描き直さない事と、地図の中身の比較 (JSON) を地図が変わった時だけにする事も、同じ理由による。

v0.1.75 までは `#ex-pos` の届く世界だけで動き、地図が届いてから 90ms で1マスを滑らせて止まっていた。
長押しで歩くと、サーバの 0.1 秒に1歩と回線の遅れの分だけ止まる間ができていた。

## 8. モダンと倍率 (v0.1.82)

窓の形の既定はモダンにした (settings.rs の `modern`)。
`modern` の無い古い settings.json もモダンで開く。

マップの倍率は 100・200・300% だけにした (settings.ts の `MAP_ZOOMS`)。
倍率は画面の実際のピクセル (devicePixelRatio) で整数倍に揃え、Windows の表示倍率が 125% や 150% でもドットの幅が揃うようにする。
表示倍率 150% で設定が 100% なら、画面のピクセルで 2 倍 (CSS の px で 1.33 倍) にする。

モダンは、v0.1.81 までのように上限のマス数で窓を覆うまで倍率を上げる事はしない。
窓を覆うマス数 (奇数へ切り上げ) をそのまま求める。
外周を足して 99 を超える時 (4K の窓を 100% で見る時など) だけ、倍率を1段ずつ上げて収める。

## 9. スムーズ移動の歩き方 (v0.1.85)

`#v6 G` を送るサーバで、スムーズ移動が有効な北固定の時は、WPHI の側で1歩ずつ歩く (ui/src/walker.ts)。
7.3 の「届いた位置を遅らせて補う」作りは、`#ex-pos` だけが届く世界でだけ使う。

- キーを押した時に、返事を待たずに1歩を送って進んだとみなし (predict.ts の `walkStep`)、地図をその位置まで滑らせる
- 1歩を滑りきるまで次の1歩を始めない。縦横の1歩は 100ms、斜めの1歩 (2行) は 200ms。サーバは 0.1 秒に1行ずつ処理するので、これより短くするとサーバより先へ進む
- キーのリピートは使わず、押している間かどうかを keydown と keyup だけで決める。窓のフォーカスが外れた時は、keyup が届かないので全部離したとみなす (map 窓は `RELEASE_ALL` を送る)。
  v0.1.87 までは、keyup が来ないまま 700ms 経つと離したとみなしていた。OS のキーリピートは最後に押したキーにしか掛からないので、上を押したまま右を押して離すと、上を押していても 700ms 後に止まった
- map 窓は keyup も main 窓へ送る (v0.1.87 までは keydown だけ)
- 歩いた1歩 (`walk 8 100ms`) と、返事を待って止まった時 (`walk wait unconfirmed=2`) をトレースに書く
- 2つの向きのキーを同時に押すと斜めに歩く。2行を続けて送り、地図は斜めに1回で滑らせる。逆向きは打ち消す。
  片方の向きだけが通れない地形なら、もう片方だけを縦横の1歩として送り、壁に沿って滑らせる (predict.ts の `pick`)。v0.1.98 までは、壁の側の1行が毎回揺れた
- 追尾移動も同じ歩き方にする。地図が 30ms ごとに送る向きが 120ms 届かなければ止まる
- 返事 (`#v6 G`) の来ていない移動が2つあれば、次の1歩を待つ。回線が遅い時にサーバより先へ行き過ぎない為
- 返事の来ていない移動は、押した向きのまま持つ。見せる位置は、`#v6 G` で確かめた位置から、残りの向きを今の地図でなぞり直して出す (predict.ts の `replay`)。
  `#v6 G` が届く度になぞり直すので、前の1歩の予想が外れても、後の1歩は本当の位置から決まる。
  v0.1.98 までは、1歩を送った時の予想の位置で進めるかを決めて結果を積んでいた。前の1歩が外れると、後の1歩を本当の位置へ足して、壁の中に見えた
- 地図の文字で通れないと分かるマスへの1歩は、進んだとみなさず、その場で 4px 寄って戻る揺れ (120ms) を見せる (predict.ts の `BLOCKED`、map.tsx の `BUMP_PX`)。
  岩 `@`、木 `T`、檻 `I`、窓 `|`、ガラス `=`、鍵の掛かった箱 `%` と扉 `{`、壁 `#` `H`。
  サーバが `T_CWALL` の印で止める地形 (phi_dm/view.rs の `move_chr`) のうち、地図の文字で分かる物。
  `go` はサーバへ送り、当たり判定はサーバが決める。壁と同じ文字で届く隠し扉をサーバが通した時は、`#v6 G` で届いた分だけ位置を直す
- 見えない所 `?`、地図の外、他のキャラやオブジェの居るマスへの1歩は、通れるか分からないので、進んだとも止まったともみなさない。揺らさずにその場で返事を待ち、返事が来るまで次の1歩を送らない (predict.ts の `uncertain`)。
  サーバが通せばそこへ滑らせ、断れば揺らす。v0.1.98 までは壁と同じく揺らして止め、サーバが通すと後から跳んだ
- 見た目が壁の隠し通路: 壁の文字 (`#` `H`) のマスへ止めた1歩をサーバが通したら、そのマスを walk の座標で覚え、以後は揺らさずに進む (predict.ts の `passed`)。
  通した直後は、同じ向きに続く壁の文字のマスも通れるとみなして進む (`tunnel`)。`#v6 G 0 0` が1度返るか、壁でないマスへ進んだらやめる。
  覚えるのは自分が通ったマスだけで、まだ見つけていない隠し通路を見せる事はしない。epoch が変わる (テレポート、タブの切り替え、接続し直し) と忘れる
- それ以外で進めなかった1歩 (深い水と浅い水が同じ `_` で届く水、透明な壁) は、`#v6 G 0 0` が届いた時に、なぞり直した位置へ 80ms で滑らせる (引き戻し)
- 通れる見た目でサーバが断ったマスは walk の座標で覚え、次からは進まずに揺らす (predict.ts の `refused`)。透明な壁の前で押し続けた時に、進んでは戻るのを繰り返さない為。
  1歩は送り続けるので、サーバが通したら (居た物が退いた、麻痺が解けた) 忘れる。epoch が変わっても忘れる
- 鍵の掛かった所への1歩も、動かない1歩として返事待ちの列に残す。`#v6 G 0 0` と順番が合わなくなる為。v0.1.84 までの、待ちきった移動の扱いにもこのずれがあった

地図は、main 窓が付けた1歩の始まりの時刻 (`walk.at`) と時間 (`walk.ms`) から、今見せている位置を起点に、その1歩の終わる時刻に着くように滑らせる。
状態が届くのが遅れても、跳ばずに次の1歩へ続く。
